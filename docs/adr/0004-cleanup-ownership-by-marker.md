# 0004 — The ownership marker, not the current schema, decides what cleanup may delete

**Status:** Proposed · **Date:** 2026-08-06 · **Tracking issue:** TBD

## Context

`removeStaleArtifacts` (`cleanup.go`) only considers file names derivable from
entities **present in the current graph** (fence 1). An entity deleted from
the schema outright therefore leaves its `_dto.go`, `_filter.go` and
`_wiring.go` behind — files carrying the entdomain marker, referencing
builders that no longer exist, breaking the consumer's build until deleted by
hand.

The comment justifying fence 1 says a deleted entity's files are
indistinguishable "from a consumer's own file". That rationale is contradicted
by fence 2 three lines down: the first-line marker
(`Code generated by entdomain extension`) distinguishes exactly that, and is
already trusted to protect hand-written files occupying generated names — the
`stale` fixture's `trinket_dto.go` exists to prove it.

## Decision

Cleanup scans the whole target directory. A file is deleted iff **both** hold:

1. its first line carries the entdomain marker (ownership — the fence that was
   always sufficient);
2. this run did not write it.

The name-derivability fence is dropped as a *gate* and kept only as the source
of the two legacy names (`_base_service.go`, `_base_handler.go`) that remain
deletable for consumers upgrading past #29 — the scan subsumes per-name
enumeration for everything current.

A consumer who wants to keep a generated file as their own removes the marker
line — an action, where today's behaviour makes keeping stale files the
default and removing them a manual chore with a build break as the reminder.

## Consequences

- Deleting an entity from the schema finally converges the consumer's tree in
  one generation run, matching what renaming an entity already does.
- The blast radius of the marker grows: any first-line-marked file in the
  target directory not written this run is deleted. The marker string is
  specific to this extension and every template emits it; ent's own files
  carry a different header and are untouched (asserted today, kept asserted).
- The `stale` fixture gains a deleted-entity case; `trinket_dto.go` keeps
  proving the negative (no marker → never touched).

## Alternatives considered

- **Fix only the comment** — honest, but leaves the one schema change that
  breaks a consumer's build (entity deletion) as the one cleanup ignores.
- **Log stale suspects instead of deleting** — cleanup already logs what it
  leaves; a log line does not fix a build.
