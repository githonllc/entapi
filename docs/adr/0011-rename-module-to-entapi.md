# 0011 — Rename the module: entdomain → entapi

**Status:** Accepted (2026-08-08, owner-adjudicated) · **Date:** 2026-08-08 ·
**Tracking issue:** — (executed in the same change) ·
**Design:** `docs/DESIGN-v3-final.md`

## Context

The module is named for its v1 annotation vocabulary (`DomainField`,
`DomainEdge`, domain scopes). v3 deletes that vocabulary entirely — the new
surface is `api.Resource()` and five deviation words — leaving "domain" only
in the module path, where it actively misleads: in industry usage (DDD),
"domain" names the business-logic layer, which is precisely what this
framework refuses to host ("transport 100%, business 0%"; the framework
never generates a service skeleton). The name promises the one thing the
design explicitly declines to provide.

The rename window is now or never-cheaply-again: zero released tags, one
known consumer (the owner's monorepo), and v3 is already a total break
(new annotation package, full regeneration).

## Decision

Rename module and repository to **`github.com/githonllc/entapi`**.

- **Why `entapi`:** ent's official extensions name the produced surface —
  `entgql`, `entproto`, `entoas`. `entapi` names this framework's product
  (the API face: DTOs, query surface, HTTP layer, OpenAPI) and joins that
  convention. `entrest` is squatted by an active same-space project
  (lrstanley/entrest); `enthttp` is too narrow (the middle layer is usable
  without HTTP); `entcrud` undersells the query surface and spec.
- Both packages stay same-named (`package entapi` at the root and in
  `runtime/`, preserving the #15 property that every call site reads
  `entapi.X`); the generated-code import alias becomes `entapi`.
- Renamed with the module: `ExtensionConfig.EntAPIPackage`,
  `WithEntAPIPackage`, the graph-level file names
  (`entapi_softdelete.go`, `entapi_errors.go`, and v3's
  `entapi_openapi.go`), and the reserved-entity-name check ("Entapi").
- **The ownership marker changes** to `Code generated by entapi extension`,
  and cleanup **recognizes the legacy marker too**
  (`Code generated by entdomain extension`) — permanently, not as a
  transition window: recognition is one string comparison, and dropping it
  would strand every pre-rename consumer tree with stale files the build
  then trips over. The consumer escape hatch (delete the marker line to own
  the file) is unchanged for both spellings.

## Consequences

- Breaking for the one known consumer: bump the import path, regenerate;
  old-marker files are cleaned up by the same run. Migration note in both
  READMEs per the established convention.
- GitHub redirects the old repository URL; historical issue links keep
  working. Local working-directory names and the project-memory path are
  not part of the module identity and migrate at leisure.
- Historical documents (`DESIGN-v2.md`, the process log in `DESIGN-v3.md`,
  ADRs 0001–0010) keep their original prose; current-facing docs (READMEs,
  CLAUDE.md, ARCHITECTURE, `DESIGN-v3-final.md`, CONTEXT.md) speak the new
  name.

## Alternatives considered

- **Keep `entdomain`** — brand continuity for a brand with zero external
  users, at the cost of a permanently misleading promise; rejected.
- **`entrest`** — most precise, but collides with an active project in the
  same niche; rejected.
- **Rename later** — cost is minimal only while there are no tags and one
  consumer; rejected.
